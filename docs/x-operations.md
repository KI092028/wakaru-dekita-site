# X（旧Twitter）運用・自動化ロードマップ

「わかる・できる」の認知拡大を目的とした、Xアカウントの運用方針と自動化計画。

作成: 2026年8月

---

## 1. 目的とKPI

### 1.1 目的

サイトの認知を広げ、**実際に使ってもらう**こと。

### 1.2 KPI

フォロワー数は目的ではなく手段である。優先順位をつけて次のように置く。

| 区分 | 指標 | 位置づけ |
|------|------|----------|
| 主KPI | サイトのセッション数、ドリル開始数 | 最終的に見たいのはこれ |
| 副KPI | Xからサイトへの流入数 | Xが機能しているかの判断 |
| 参考 | インプレッション、フォロワー数、エンゲージメント率 | 投稿の型を改善するための材料 |

**フォロワーが増えてもサイトに人が来ていなければ、運用は失敗している。**
この前提を月次の振り返りで毎回確認する。

## 2. 前提条件（2026年8月時点）

### 2.1 X APIの料金体系が2026年2月に変わっている

**無料枠は新規開発者には提供されていない。** 従来のFree/Basic/Proという月額制は
新規受付を終了し、**従量課金（pay-per-use）が既定**になった。

| 操作 | 単価 |
|------|------|
| ポスト作成（テキスト・画像、**URLなし**） | $0.015 / 回 |
| ポスト作成（**URLを含む**） | **$0.20 / 回** |
| ポストの読み取り | $0.005 / 件 |
| ユーザー情報の読み取り | $0.010 / 件 |

出典: [X API公式ドキュメント](https://docs.x.com/x-api/getting-started/pricing) /
[発表スレッド](https://devcommunity.x.com/t/announcing-the-launch-of-x-api-pay-per-use-pricing/256476)

> 単価は変動しうるため、着手時に必ず公式ドキュメントで再確認すること。
> 初期クレジットの購入単位や最低課金額の有無も申込時に確認する。

### 2.2 ここから導かれる設計原則

**URLを含むポストは、含まないポストの約13倍のコストがかかる。**
したがって次を原則とする。

- **日常の投稿にはURLを入れない。** サイトへの導線はプロフィール欄のリンクに集約する
- URLを入れるのは、**新単元の公開など「告知」の場面に限る**（月1〜2回程度）

これはコスト面だけの話ではない。Xは外部リンクを含む投稿の表示を抑制する傾向があるため、
**リンクを入れない方が結果的に多くの人に届く。** コスト最適と到達最適が一致している。

### 2.3 想定コスト

上記の原則で運用した場合の月額目安。

| 内訳 | 回数/月 | 単価 | 小計 |
|------|---------|------|------|
| 毎日の1問（URLなし） | 30 | $0.015 | $0.45 |
| 告知ポスト（URLあり） | 2 | $0.20 | $0.40 |
| 指標の読み取り | 30 | $0.005 | $0.15 |
| **合計** | | | **約 $1.0（約150円）／月** |

**API費用は懸念していたほど大きくならない。** ただしそれは「日常の投稿にURLを入れない」
という前提の上に成り立つ。毎日リンク付きで投稿すると月$6超になり、費用構造が変わる。

### 2.4 手動投稿は無料である

Xのアプリ・Webからの投稿・返信・DMは**APIを介さないため一切課金されない。**
自動化は「手間を減らす手段」であって、「無料でやる手段」ではない。
低頻度の運用なら、そもそも自動化しない選択も合理的である。

## 3. 役割分担

### 3.1 Claudeができること・できないこと

| できる | できない |
|--------|----------|
| 自動投稿の仕組み（GitHub Actions）を実装する | 常時稼働して24時間アカウントを見張る |
| 投稿文のテンプレートや文面を作る | セッションが終わった後に自律的に動く |
| 問題画像を生成する仕組みを作る | この開発環境から外部APIを呼ぶ（ネットワーク制限のため） |
| 蓄積した指標を分析し、月次レポートを書く | 人間の判断が要る対応（炎上時など）を代行する |

**重要**: 自動投稿の実体は**GitHub Actionsのスケジュール実行**であり、Claudeのセッションではない。
Claudeの役割は「仕組みを作る人」と「定期的に分析する人」である。

月次の分析は、スケジュール実行（Routine）で自動的にセッションを起動させることができるため、
「毎月1日にClaudeが起きてレポートを書く」という形は実現可能。

### 3.2 人（運営者）がやること

- アカウントの開設と初期設定、API利用の申込みと支払い設定
- **通知の確認と、返信・DMへの手動対応**（→ 4.3）
- 月次レポートを読んで、運用方針の最終判断をする
- 炎上・誤情報など、判断が必要な事態への対応

## 4. 運用方針

### 4.1 投稿の種類

サイト更新の告知だけでは**月1〜2回しか投稿できず、アカウントは伸びない。**
定期的に価値を出す投稿が必要になる。

| 種類 | 頻度 | URL | 内容 |
|------|------|-----|------|
| **毎日の1問** | 毎日 | なし | 既存の出題エンジンで生成した問題を画像で投稿。「答えは何でしょう？」 |
| **つまずき解説** | 週1 | なし | 通分・約分など、子どもがつまずく箇所の考え方 |
| **新単元の告知** | 公開時 | あり | 新しいドリルの公開を知らせる |
| **月次のふりかえり** | 月1 | なし | 「今月は◯人が挑戦しました」など |

**毎日の1問**が中心になる。既存の `lib/quiz/` の出題ロジックと、OGP画像で構築した
画像レンダリングの仕組みをそのまま流用できるため、追加コストがほとんどかからない。

画像には必ず**代替テキスト（alt）に問題文を入れる**。読み上げ環境への配慮であり、
テキストとしても検索に引っかかる。

### 4.2 発信者の人格

**未確定（→ 8章）。** 「サービス公式」として書くか、「作った本人」として書くかで
文体も伸び方も変わる。個人の顔が見える方が拡散されやすく、
特に「教育現場での経験に基づいて作った」という背景があるなら強い訴求になる。

### 4.3 返信・DMについて（方針の修正提案）

**ご提案の「返信・DM対応はしない」について、一部修正を提案する。**

- **自動化しないという判断は正しい。** 返信の自動生成は誤爆のリスクが高く、
  APIの読み取りコストもかかる。ここは同意する
- **ただし「対応しない」とは分けて考えたい。** Xアプリからの手動返信は**無料**である
- 質問や感想を無視し続けるアカウントは、認知拡大の観点で明確にマイナスになる

したがって次を方針とする。

> **返信・DMの自動化は行わない。ただし通知は人が定期的に確認し、
> 必要なものには手で返す。** 頻度は週1回程度で十分。

これによりAPIコストは増えず、アカウントの印象は大きく変わる。
また、当面はこれが**フィードバック窓口**を兼ねる（→ requirements.md 10.2）。

## 5. 計測の設計

### 5.1 現状のギャップ

**サイトには現在アクセス解析が入っていない。** このままではXから何人来たのか、
来た人がドリルを解いたのかが一切わからない。
「クリック数を検証する」ためには、**投稿を始める前に**計測を用意する必要がある。

### 5.2 何を入れるか

サイトの立て付けが「登録不要・データを取らない」である以上、
**Cookieを使わない解析ツール**を選ぶ。Google Analyticsは高機能だが、
Cookieを使い個人追跡の色が強く、保護者向けの訴求と相性が悪い。

候補: Cloudflare Web Analytics（無料・Cookieなし）、GoatCounter など。

導入時には**プライバシーポリシーの追記が必要**（現在は「使用する場合があります」との
記載にとどまるため、実際に入れたら具体的に書く）。

### 5.3 UTMパラメータ

告知ポストのリンクには必ずUTMを付け、流入を判別できるようにする。

```
https://wakaru-dekita-site.com/?utm_source=x&utm_medium=social&utm_campaign=fractions-release
```

### 5.4 月次レポートの項目

| 区分 | 項目 |
|------|------|
| X側 | インプレッション、エンゲージメント率、フォロワー増減、プロフィールクリック数 |
| サイト側 | セッション数、Xからの流入数、直帰率、ドリルページの閲覧数 |
| 考察 | 反応が良かった投稿・悪かった投稿とその要因、翌月に試すこと |

X側の指標は、**API経由でなくX標準のアナリティクス画面から取得できる**（無料・項目も豊富）。
自動収集にこだわらず、当面は手動での取得で十分。

## 6. ロードマップ

### フェーズ0: 土台づくり（自動化の前にやる）

**ここを飛ばして投稿を始めると、初期のデータが取れず後から検証できない。**

1. サイトに解析を導入し、プライバシーポリシーを更新する
2. Xアカウントを開設し、プロフィールを整える
   - アイコン: 作成済みのファビコン（オレンジの「わ」）を流用
   - ヘッダー画像: OGP画像をベースに作成
   - bio、固定ポスト、プロフィールのリンク（**ここが常設の導線になる**）
3. **2〜3週間、手で投稿して運用してみる**
   - 開設直後のアカウントがAPIで自動投稿を始めると、スパム判定を受けるリスクがある
   - どんな投稿が反応されるか、自動化する前に手で掴んでおく
4. X開発者アカウントを申請し、支払い設定を済ませる

### フェーズ1: 告知の自動化

- サイトのデプロイ完了をトリガーに、新単元の公開を自動投稿する
- GitHub Actionsから実行。認証情報はリポジトリのSecretsに保存する
- 頻度が低く、リンク付きでも費用はごくわずか
- **最小の自動化。ここで仕組みの動作を確認する**

### フェーズ2: 毎日の1問の自動化

- 既存の出題ロジックで問題を生成し、画像に描画して毎日投稿する
- URLは入れない
- 重複を避けるため、出題履歴をリポジトリに記録する
  （Xは同一内容の連投を規約違反として扱う）

### フェーズ3: 月次レポートの自動化

- 指標を収集してリポジトリに蓄積する
- 毎月1日にスケジュール実行でClaudeのセッションを起動し、
  蓄積データから分析レポートを作成、運用方針の見直し案を提示する
- 最終判断は人が行う

### フェーズ4: 改善サイクル

- 反応の良かった投稿の型を増やし、悪かった型を減らす
- 単元の追加ペースと投稿計画を連動させる

## 7. リスクと対策

| リスク | 対策 |
|--------|------|
| 開設直後の自動投稿でスパム判定・凍結 | フェーズ0で手動運用の期間を置く。投稿間隔を空ける |
| 同一内容の連投による規約違反 | 出題履歴を記録し、重複を避ける。文面にも変化をつける |
| APIコストの想定外の増加 | URL付き投稿の回数を監視する。上限アラートを設定する |
| 認証情報の漏洩 | GitHub Secretsで管理し、コードに直書きしない |
| 自動投稿の誤爆（誤った内容の投稿） | 投稿前に問題と答えの整合性を機械的に検証してから投稿する |
| 子ども向けサービスとしての体裁 | 過度に煽る表現を使わない。誤答を笑うような文面にしない |

X の自動化に関する規約（Automation Rules）を遵守する。
自動投稿するアカウントには、設定で**自動化アカウントのラベル**を付けることが望ましい。
