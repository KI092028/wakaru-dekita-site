## 2. 目的とコンセプト

**「わかった」「できた」という達成感を、短いサイクルで積み重ねられる場をつくる。**

- 1問あたり10秒程度、1セット10問で完結する
- 説明を読ませるのではなく、すぐ問題に取り組める
- 正解・不正解をその場で返し、最後に点数で振り返る

### 想定する利用シーン

- おでかけ前、待ち時間などの**すきま時間**
- 宿題の前後、自主学習の時間などの**おうち学習**

### 5.2 ドリルの共通仕様

出題・判定・進行の挙動は**3単元で完全に共通**。実装も `components/quiz/quiz-game.tsx` 1つに集約している。
単元ごとに違うのは「問題の作り方」と「九九マップを出すかどうか」だけ。

- **1セット10問**。ページを開いた時点で10問を用意する
- **答えは選ばせず、画面内の数字キーパッドで打たせる**（選択肢は持たない）。
  端末のキーボードは出さない（低学年には操作が難しく、画面が覆われる）
- 整数は1枠、分数は**分子・分母の2枠**。分数の枠はタップで切り替えられるほか、
  右下の大きいボタンが分子入力中は「ぶんぼへ」に変わる
- 先頭の 0 は「0」単独のときだけ許す（ひき算の答えが 0 になりうるため。「05」は入力できない）
- **分数は約分し終えた形だけを正解とする。** `2/4` は誤答として扱い、約分をうながす
- 正解すると「せいかい！」を出し、**約0.55秒で自動的に次の問題へ進む**（「つぎへ」は押さない）
- 不正解のときは止まり、次の3つを出す
  1. 誤答の型が分かれば**何を間違えたか**を1行で言う（→ 5.3）
  2. 正答
  3. 「もういちど うってみる」ボタン
- 打ち直し（訂正的検索）で正しく入力すると次へ進む。**このときは得点も習得記録も動かさない**
- 画面上部に「n / 10 もん目」と「とくてん」を常時表示する
- 10問終えると結果画面に切り替わり、**n / 10 もん**の形式で得点を表示
- 「もういちど挑戦する」で**新しい10問**を用意して最初から再開する

### 5.3 誤答の型を返す

不正解のとき、打たれた答えの形から何を間違えたかを判定して1行で返す（`lib/quiz/diagnose.ts`）。
判定できないときは正答の提示だけにとどめる。

| 単元 | 拾っている誤答 | 返す言葉 |
|------|----------------|----------|
| 九九 | `a×(b±1)` / `(a±1)×b` | 「おしい！ ◯のだんの ひとつ となりの こたえだよ」 |
| 九九 | `a+b` | 「たし算に なっているよ。ここは かけ算だね」 |
| たし算・ひき算 | 逆の演算の答え | 「しるしを 見てみよう。ここは たし算だよ」 |
| たし算・ひき算 | 正答との差が 10 | 「くり上がり／くり下がりを わすれていないかな」 |
| たし算・ひき算 | 正答との差が 1 | 「あと 1 だけ ちがうよ。かぞえまちがいかも」 |
| 分数 | 値は合っているが約分前 | 「あと ひといき！ その分数は もっと かんたんに できるよ」 |
| 分数 | 分子どうし・分母どうしを計算 | 「ぶんしどうし・ぶんぼどうしを 計算していないかな。さきに つうぶんだよ」 |
| 分数 | 通分はしたが分子を直し忘れ | 「つうぶんは できているね。ぶんしにも 同じ数を かけよう」 |
| 分数 | 分母だけ合っている | 「ぶんぼは あっているよ。ぶんしを もういちど」 |

ここに並ぶ誤答は、4択時代に「誤選択肢」として持っていた知識をそのまま移したもの。
選択肢は廃止したが、**つまずきの型という資産は捨てていない。**

#### 分数の設計（実装済み）

子どもがつまずくのは計算そのものより、**通分と約分の作業**である。
そのため同分母の計算だけでは実際の弱点に効かない。1セット10問の中で、
レベル選択のUIを設けずに次の順で難しくしている。

1. 同分母のたし算・ひき算（導入・2問）
2. 片方の分母がもう片方の倍数（通分の入口・3問）
3. 最小公倍数で通分（つまずきの本丸・3問）
4. 答えの約分が必要（2問）

**答えは既約分数でのみ正解とする。** 2/4 のような約分前の形は誤答として扱い、
「もっとかんたんにできる」と返す。約分こそがこの単元の練習対象なので、
値が合っていれば通す作りにすると素通りできてしまう。

子どもが実際にやりがちな間違い（「分子どうし・分母どうしを足す」など）は、
かつて誤選択肢として持っていたが、いまは誤答の型として `diagnose.ts` に置いている（→ 5.3）。

問題として提示する分数は既約にそろえる。3/6 − 1/6 のように問題側が約分できると、
答えを約分する練習の前に問題を約分してしまい、何を問われているかがぼやけるため。

#### 単元構成の考え方

将来的には、**教科書における小学校6年間の単元構成の順番**に沿って問題を用意したい。
学年ごとに何を学ぶかの流れに沿って単元が並んでいれば、
「今習っているところ」を選びやすくなる。

現時点の単元一覧は少数の単元を並べているだけだが、
単元が増えてきた段階で、学年・履修順を持たせた構成へ整理する。

準備中の単元はカードを淡色表示し、リンクを持たせない。
`lib/quiz/units.ts` の `available: false` で制御している。

お問い合わせフォームも未実装（`/contact` は準備中の案内のみ）。

### 5.6 九九マップ（九九のみ）

81マスの習得状況を持つのは九九だけ。他の2単元は毎回ランダムに出題する。

> **注意: マップ・コンボ・テンポ改善は手応えを生まなかった。**
> 原因を理論と実証から調べた結果を [game-design-research.md](./game-design-research.md)、
> [cognitive-science-research.md](./cognitive-science-research.md)、
> [concept-review.md](./concept-review.md) にまとめてある。
> 要点は「マップ・コンボ・テンポ改善はいずれも中核の体験の外側に置いた層であり、
> 中核（選択肢から選ぶだけ・意思決定なし・リスクなし）を変えていなかった」こと。
> **本節を実装の指針として読む前に、必ず調査文書を参照すること。**

#### しくみ

- 九九ページの上部に **9×9＝81マスの表**を置き、各マスの習得状況を色で示す
- 状態は 未挑戦 / れんしゅう中 / マスター / にがて の4つ
- **連続2回正解でマスター。** かつては「4択では偶然当たるから2回」という理由だったが、
  入力式にしたいまは「1回の正解では定着とは言えず、別のセットでもう一度出会って
  正解する必要がある」という理由で2回にしている
- **一度マスターしたマスは、あとで間違えても取り消さない。** マスター数が減るのは罰になる
  （ただし出題では優先的に再登場させる）
- 結果画面に「あたらしく◯マス マスターしました」「のこり◯マス」を表示する

#### 出題の優先順位

にがて → **あと1回でマスター** → 未挑戦 → マスター済み（復習）

「あと1回でマスター」を未挑戦より先に出すのが要点。未挑戦から消化すると
81マスを一巡するまでマスターが1つも増えず、進んでいる実感が出ない。
さらに「あと1回」と「未挑戦」を交互に混ぜることで、
毎回およそ5マスずつ安定してマスターが増えるようにしている。

#### コンボ表示は撤去した

「◯れんぞく」の表示は、調査で**苦手な子ほど失敗の可視化装置として働く**と指摘されており、
3単元の操作感をそろえる際にあわせて撤去した。他単元へ広げる選択肢もあったが、
効果がないと分かっているものを広げる理由がない。

#### 採用しなかったゲーム性と、その理由

| 要素 | 見送った理由 |
|------|-------------|
| デイリーストリーク（連続日数） | 再訪動機としては強いが、**通知を送れない静的サイトでは機能しにくい**。途切れたときの罪悪感も低学年には重い |
| タイムアタック | 焦りでミスが増え、算数嫌いの原因になりうる |
| ランキング・他者比較 | 低学年では劣等感につながり学習を阻害する。そもそもサーバーがないため実現もできない |
| ガチャ・コレクション報酬 | 射幸性が高く、保護者の信頼を損なう |

#### 保存について

習得状況は **端末のlocalStorageにのみ**保存する（キー: `wakaru-dekita:times-table:v1`）。
サーバーには送らない。端末やブラウザを変えると引き継がれず、
ブラウザのデータ削除で消える。この点は**画面上とプライバシーポリシーの両方に明記**している。

localStorageが使えない環境や保存内容が壊れている場合は、
記録なしとして扱い、学習そのものは続けられるようにしている。

### 5.7 わり算のひっ算

3単元のドリルとは性質が違う。**1問1答ではなく手続きの練習**なので、
答えだけを合わせても意味がない。UIも別に用意している（`components/division/`）。

#### つまずきを4つに分けて扱う

わり算のひっ算でつまずく子は、「わり算ができない」のではなく、
次のどれかで止まっていることが多い（現場での見立て）。

1. **九九がパッと出ない** — 手順を追う余力が九九の思い出しに取られる
2. **手順そのものを覚えていない** — たてる・かける・ひく・おろす の順が定まらない
3. **どこに商を立てるか分からない** — 位取りの理解
4. **ひき算（くり下がり）で崩れる**

これらは別々の力なので、まとめて「不正解」にすると本人にも何ができていないか分からない。
そこで1手ごとに区切り、**どの手で止まったかを別々に数える**。

| つまずき | 手当て |
|----------|--------|
| 九九が出ない | 除数の段の九九を、開けば見られるようにする（既定は閉じる）。ここでの目的は手順の習得なので、九九は見てよいことにした |
| 手順を覚えていない | **たてる→かける→ひく→おろす を常に画面に表示**し、いまどれかを示す。手順を思い出すことに気を取られて計算が崩れるのを防ぐ |
| 商を立てる位置 | 最初に「商はどこに立つか」を、ひっ算の上のわくをタップして答えさせる。ずれたら「ひとつ右だね」と方向を返す |
| くり下がり | ひくの手で、たし算・ひき算の誤答診断をそのまま使う |

#### 出題

1セット**4問**。ひっ算は1問に何手もかかるため、10問だと最後まで持たない。
段階は固定で、つまずきの種類ごとに1問ずつ当たるようにしてある。

問題は、条件に合うものが出るまでランダムに引いては手順を組んで確かめる方式で作る。
段階の判定にひっ算の手順そのものを使うほうが、条件を数式で書き下すより間違いが少ない。
いちばん当たりにくい段階でも20回に1回は当たるので、数十回引けば足りる
（全組み合わせを先に並べる作りにすると、端末で7万通り分の計算が走るためやめた）。

| 順 | 内容 | ねらい |
|----|------|--------|
| 1 | わりきれる2けた÷1けた | 手順そのものに集中させる。商に0が立つ形は避ける |
| 2 | あまりのある2けた÷1けた | ひく の意味 |
| 3 | 3けた÷1けた・はじめのけたで割れない | どこに商を立てるか |
| 4 | 3けた÷1けた・商に0が立つ | いちばんの難所 |

#### 2けたでわる（別単元）

**1けたでわる／2けたでわるは別のページに分ける**（教科書でも3年と4年で分かれている）。
2けたでわるほうは「仮の商の見当をつけて、合わなければ1つ増減する」という
別の技能が中心なので、同じセットに混ぜると何を練習しているのかがぼやける。

出題の段階：

| 順 | 内容 | ねらい |
|----|------|--------|
| 1 | 仮の商がそのまま合う | がい数で見当をつけるやり方に慣れる |
| 2 | 仮の商を1つ減らす | 23 を 20 と見たぶん、仮の商が大きく出る |
| 3 | 仮の商を1つふやす | 19 を 20 と見たぶん、仮の商が小さく出る |
| 4 | 商が2けた | 段を2回まわす |

2けたでわるときだけ足しているもの：

- **たてる の手で、がい数のつけ方を毎回画面に出す**
  （「24 は だいたい 20。336 ÷ 20 で 見当を つけよう」）。
  覚えているかを試す場面ではないので、手順は見せてしまう
- 商がずれたときは「大きすぎる／小さすぎる」で終わらせず、
  **「ひとつ 減らしてみよう」「ひとつ ふやしてみよう」**と次の動作まで言う。
  仮商の修正こそがこの単元の中心なので
- かける の誤りは九九ではなく**2けた×1けた**の誤りとして見る。
  となりの積・くり上がりのたしわすれ・一の位だけ／十の位だけ を拾う
- ひく の誤りは、くり下がりの取りこぼしが 10・100 のずれとして出るのを拾う
- 打てる桁数を手ごとに変える（商は1けた、かけた数は3けたまで）
- 補助の表の見出しは「52 のだん」ではなく「52 × 1〜9 を 見る」にする

#### ドリルとそろえたところ／変えたところ

**そろえた**: 画面内の数字キーパッド、間違えたら止まって指摘＋正答、
「もういちど やってみる」で自分で打ち直す流れ、言い回し。

**変えた**: 正解しても間を置かず、すぐ次の手へ進む。
ひっ算は1問が長いので1手ごとに演出を挟むとテンポが死ぬ。
**書き足された数字が盤面に現れること自体が手ごたえになる**ため、演出は問題の完成時にまとめる。

#### 結果の見せ方

ひっ算は途中で投げ出さないかぎり必ず完成するので、「n問正解」は意味を持たない。
かわりに次の2つを出す。

- **1回で最後までできた問題数**（間違えずに通せたか）
- **まよったところの内訳**（たてる◯回／かける◯回…）

そのうえで、いちばん多かったつまずきに応じて戻る先を名指しする。
かける でつまずいていれば九九へ、ひく でつまずいていればたし算・ひき算へリンクする。
回数が同じときは**九九・ひき算を先に見る**。この2つだけが別の単元で直接練習できる＝
打ち手のあるつまずきだから。

#### 記録

**手ごとに「通った回数」と「止まった回数」を端末に保存する**。1セット通し終えた時点で書き足す。
1けたでわる／2けたでわるは別単元なので、記録も別のキーに分ける
（`wakaru-dekita:long-division:v1` / `wakaru-dekita:long-division-2:v1`）。

1回分の結果だけでは「たまたま間違えた」と区別がつかない。
何回やっても同じ手で止まっているのかが分かって、はじめて見立てになる。

- 見るのは回数ではなく**割合**。「かける 3回」は、かけるを何回通ったかが分からないと
  多いのか少ないのか判断できない
- 通った回数が **6回に満たない手は対象から外す**。1〜2回のつまずきで
  「ここが苦手」と決めつけないため
- 直近5セットぶんだけ「どの手で止まったか」を覚えておき、
  「さいきんの3回のうち3回」という形で出せるようにしている

**表示は結果画面だけにとどめる。** 常に見える場所に「苦手: かける」と出すのは、
コンボ表示と同じく失敗の可視化装置として働きうる。
言い方も不足ではなく方向として書く（「九九を すこし れんしゅうすると 楽になる」）。

保存は九九と同じ扱い。localStorage が使えない環境や内容が壊れている場合は
記録なしとして扱い、練習そのものは続けられるようにしている。
端末内にのみ保存する旨は**結果画面とプライバシーポリシーの両方に明記**している。

### 5.8 教員向けエリア（`/teachers/`）

児童向けドリルとは**読者が違う**ため、URLとナビゲーションで分離している。
設計の経緯と掲載内容は [class-rec-spec.md](./class-rec-spec.md) を参照。

#### 分離の仕方

- **ヘッダーには出さない。** 児童が見るナビゲーションは変えない
- 導線は**フッターの「先生の方へ」1リンク**のみ。教員は検索から
  `/teachers/rec/` に直接着地する想定なので、トップからの導線に依存しない
- 文体を切り替える。ドリルはひらがな主体だが、ここは通常の漢字表記

#### 学級レクの掲載条件

数を並べることを目的にしない。次を**すべて**満たすものだけ載せる。

1. 5分以内に終わる（説明込み）
2. 準備物が「なし」または「黒板とチョーク」まで
3. 教室で成立する（体育館・校庭を必要としない）
4. ルール説明が30秒で済む
5. 人数が多少ぶれても成立する

体育館ありが混ざっていて、隙間時間に開いた教員には大半が使えないため。

**「声の大きさ」が要点。** 隣のクラスが授業中だと、盛り上がるレクは候補から外れる。

`relatedUnit` を持つものは詳細ページから該当ドリルへリンクする。

### 5.9 たし算・ひき算のひっ算／小数のたし算・ひき算

わり算のひっ算と同じ「1手ずつ進める手続きの練習」。実装は `lib/column/` と
`components/column/` にまとめ、**整数と小数を同じ部品で扱う**（`ColumnGame mode="integer" | "decimal"`）。

わり算は「段」で進むが、こちらは**位ごとに右から左へ**進む。構造が違うので
`lib/division/` とは型を共有していない。共有しているのはキーパッド・誤答時の流れ・記録の仕組み。

#### 手を3〜5種類に分ける

| 手 | 内容 | 入力 |
|----|------|------|
| `write` | その位の答えを書く | 数字 |
| `carry` | くり上がりの1を**ひとつ左の位の上に置く** | 位のタップ |
| `borrow` | 借りたあと、左どなりがいくつになるかを書く | 数字 |
| `pad` | けたをそろえる 0 を書く（小数のみ） | 数字 |
| `point` | 答えの小数点を打つ（小数のみ） | すきまのタップ |

**くり上がりを数字入力ではなく位のタップにしてある。** 書く数（1）は決まっていて、
つまずくのは「どこに書くか」のほうだから。小数点も同じ理由ですきまを選ばせる。

#### その位の計算をまとめて打っても正解にする

1 + 7 + 8 の位で **16 と打つのを正解として受け取る**（書かれるのは一の位の 6）。

頭の中では 16 まで出してから 6 を書き 1 をくり上げるので、16 と打つのは
手順が分かっていない証拠ではなく、むしろ自然な打ち方。
かつてはこれを誤答として「16 のうち この位に 書くのは 6 だけ」と返していたが、
**正しく計算できた子に「ざんねん」を返していた**ことになる。

くり上がりの手の問いは「16 の くり上がりの 1 は どこに 書く？」とし、
まとめて打った子にも、6 だけ打った子にも同じようにつながるようにしてある。
かけ算のひっ算の九九の手（42 と打つ）も同じ扱い（→ 5.10）。

ひき算の誤答診断には Brown & Burton (1978) が挙げた代表的な手続きのバグを入れている。
中でも**上下をひっくり返して引く**（ひけないので大きいほうから小さいほうを引く）は
最も多いので、専用の言葉を返す。

#### 小数で足していること

つまずきは計算ではなく**そろえる作業そのもの**にあるので、計算より先にそろえさせる。

- けたが足りない側に 0 を書き足す手（`pad`）を先頭に置く
- 続いて**答えの小数点を打つ位置**を決めさせる。上下の小数点とたてにそろう位置を選ばせる
- ただし盤が2けたしかない（すきまが1つしかない）ときは選ぶ余地がないので、
  手として問わず最初から打っておく
- 内部では 10ⁿ 倍した整数として扱い、整数のひっ算の手順をそのまま使う

#### 出題

1セット**6問**（わり算より1手あたりが軽いので4問ではなく6問）。段階は固定。

整数：くり上がりなし → くり上がり1回 → くり上がり2回（3けた）→
くり下がりなし → くり下がり1回 → くり下がり2回（3けた）。

**くり上がり／くり下がりは一の位から起きる形に限る。** 十の位だけでくり上がる問題
（54+83）は指導の順序が違うため、この段階では出さない。
0のとなりから借りる形（302−158）は借りが2つ左まで連鎖する別の難所なので出さない。

小数：小数第1位どうし（くり上がりなし／あり）→ けた数がちがうたし算 →
同じ3段階のひき算。**けた数がちがう形**を必ず1問ずつ入れて、そろえる練習にする。

記録は単元ごとに別キー
（`wakaru-dekita:column-add-sub:v1` / `wakaru-dekita:column-decimal:v1`）。
仕組みは 5.7 と同じで、`lib/practice/record.ts` を共通で使う。

### 5.10 かけ算のひっ算

盤の作りが他と違う。たし算・ひき算は1行で答えが出るが、かけ算は
**かける数のけたごとに1行（部分積）**ができ、最後にそれを足す。
そのため盤だけは別に用意している（`components/multiply/multiply-board.tsx`）。
最後のたし算は、たし算のひっ算の手順（`buildColumnPlan`）をそのまま使う。

#### 手を4つに分ける

| 手 | 内容 | 入力 |
|----|------|------|
| `product` | その位の九九の答えを書く（10以上なら一の位だけ） | 数字 |
| `carry` | くり上がりを**ひとつ左の上に書きとめる** | 数字 |
| `shift` | 2だんめを**どこから書きはじめるか** | ますのタップ |
| `add` | 部分積どうしを足す | 数字 |

**`shift` を独立した手にしてあるのが、この単元の中心。**
「なぜ1つずらすのか」が分からないまま形だけ覚えている子はここで必ず止まるので、
それが記録に残る。誤答には方向を返す
（「2だんめは かける数の 十の位を かけているね。だから ひとつ 左から 書きはじめるよ」）。

たし算のくり上がりが**位のタップ**なのに対し、かけ算のくり上がりは**数字入力**。
書く数が 1 で固定ではなく 0〜8 になるうえ、その値を出すこと自体が練習だから。

いちばん左からあふれるけたは、上に書かずそのまま答えの位に書く（紙のひっ算と同じ）。
書きとめる場所がないので、**直前の計算を問いの中で示す**
（「2 × 8 + 5 = 21。くり上げる 数を、いちばん 左に 書こう」）。

#### 出題

1セット**4問**。2けた×2けたは1問13手あるため、6問だと最後まで持たない。

| 順 | 内容 | ねらい |
|----|------|--------|
| 1 | 2けた×1けた・くり上がりなし | 手順そのものに集中させる |
| 2 | 2けた×1けた・くり上がりあり | くり上がりを書きとめる |
| 3 | 2けた×2けた・くり上がりなし | **ずらすことだけに集中させる** |
| 4 | 2けた×2けた・くり上がり2回以上 | 通しでできるか |

一の位が 0 の数は九九の手がひとつ消えるので使わない。
3問目は、かけられる数の十の位と一の位が同じ数（22×31）も避ける
——全部同じ九九になり、考えずに同じ数を書けてしまうため。

九九の手では、**まとめて打った値（7×6 を 42）も正解にする。**
理由は列のひっ算と同じ（→ 5.9）。単元ごとに扱いを変えない。

記録は `wakaru-dekita:column-multiply:v1`。戻る先は
`product` なら九九、`add` ならたし算のひっ算へリンクする。

### 5.11 角の大きさ（分度器）

ここまでの単元と種類が違う。**答えを出す手続きではなく、道具の当て方**を練習する。
分度器の使い方は説明を読んで分かるものではなく、ずれた状態から自分で合わせてみないと
身につかない。紙の上では教師が横について直すしかない場面で、
画面ならその役をある程度まかなえる、というのがこの単元を作った理由。

#### 手を3つに分ける

| 手 | 内容 | 操作 |
|----|------|------|
| `place` | 分度器の中心を、角のいただきに合わせる | 分度器をドラッグ（平行移動） |
| `align` | まっすぐなへり（0の線）を辺にかさねる | 分度器をドラッグ（中心まわりの回転） |
| `read` | 目もりを読む | 数字キーパッド |

**同じドラッグに、手ごとに違う意味を持たせている。** 移動と回転を同時に扱わせると
指が3方向に取られて、何をしているのか分からなくなるため。
`read` の手では分度器は動かせない。**自分が置いた分度器のまま読ませる**ことが要点で、
きれいに当たった状態を用意して読ませるのでは、当て方の練習にならない。

手が終わるたびに、ぴったりの位置・向きに寄せる（スナップする）。
わずかなずれを残したまま目もりを読ませても読み方の練習にならないため。

#### 合わせ方は2通りとも正解にする

まっすぐなへりの**右はしを辺に合わせても、左はしを合わせてもよい**。
そのとき 0 から数える目もりが入れかわるだけで、読み取れる角の大きさは同じ。
**これが目もりが2しゅるいある理由そのもの**なので、両方を通す。

内側と外側の読み違い（60度を120度と読む）は、この単元で最も多いつまずき。
「内側を見なさい」ではなく、**自分が 0 を合わせたのはどちらのはしか**に立ち返らせる。

そのうえで、**左の 0 を使わないと自然に解けない問題を半分入れている。**
水平な辺が右向きの図ばかりだと、右の 0 だけで最後まで通せてしまい、
目もりが2しゅるいある理由に一度も出会わずに終わる。
水平な辺を左向きにすると、右の 0 では角が半円に入らないので、
**左の 0 を使うか、分度器をひっくり返すか**を自分で決めることになる。

このとき「へりは辺に重なっているが、角が分度器の外に出ている」置き方を必ず通る。
ここは「へりがずれている」ではなく **「ひっくり返そう」** と言わないと、
何を直せばよいのか分からない。専用の言葉を返している。

> 0 を 合わせた 辺から 数えよう。いま 0 は 右はし に あるから、
> 右はしの 0 から 進む ほうの 目もりだよ

この言い方なら、左はしに合わせた子には「左はし」と返る。
分度器の作り（どちらの環が内側か）にも依存しない。

#### 出題

1セット**6問**。1問3手と短いので、ひっ算より多くとれる。
**右の 0 を使う形と、左の 0 を使う形を3問ずつ**にしてある。

| 順 | 内容 | ねらい |
|----|------|--------|
| 1 | 鋭角・右に0・水平 | 当て方そのものに集中させる |
| 2 | 鈍角・右に0・水平 | 内側・外側の読み違いが出る |
| 3 | 鋭角・左に0・水平 | ひっくり返す必要に出会う |
| 4 | 鈍角・左に0・水平 | 左の 0 から数える |
| 5 | 直角に近い角・かたむき（右に0） | 90度ちょうどは避ける（分度器を使わずに分かるため） |
| 6 | 鈍角・かたむき（左に0） | 通しでできるか |

はじめの分度器の向きは、**2つある正しい向きのどちらからも25度以上離す。**
片方しか見ていないと、たまたま最初から合っている問題が出る。

図の外わくは、**分度器がどちらを向いても収まる大きさ**にとってある
（いただきを中心に半径130の円が入る 400×380）。
上向きだけを想定した大きさだと、左の 0 の問題で半円が下を向いたときに
分度器が画面の外に出てつかめなくなる。

**角の大きさは5の倍数に限る。** 4年では1度きざみまで読むが、
画面では半径130pxに180本の目もりが並び、1度の差は指では読み分けられない。
ここで測るのは当て方と「どちらの目もりを見るか」なので、
読みの細かさを問うのは紙にゆずる。

記録は `wakaru-dekita:angle:v1`。他の単元へのリンクは持たない
（分度器の当て方を練習し直せる場所が、サイト内にここしかないため）。

## 6. 非機能要件

### 6.1 プライバシー・安全性

保護者に安心して使ってもらうため、以下を設計上の前提とする。

- **アカウント登録・個人情報の入力を一切求めない**
- **解答結果をサーバーに送信・保存しない**。すべてブラウザ内で処理して完結する
- 静的サイトのため、そもそも入力を受け取るサーバー処理を持たない
- 子どもが使うことを踏まえ、過度な広告表示は行わない

### 6.2 パフォーマンス

- 静的サイト（事前生成）として配信する
- First Load JS の目安: 静的ページ 約87KB / ドリルページ 約105KB
- 全ページを事前生成し、実行時のサーバー処理を持たない

### 6.3 対応環境・UI

- **スマホ・タブレット・PC** に対応（レスポンシブ）
- 子どもが操作することを踏まえ、**選択肢ボタンは高さ64px** と大きめに確保する
- 問題文は特に大きく表示する（4xl）

### 6.4 表記・トーン

- 言語は日本語。`<html lang="ja">`
- 対象学年に配慮し、ドリル画面まわりは**ひらがな主体**にする
  （例: 「もんだいを準備しています…」「せいかい！」「ざんねん…」「とくてん」「たんげんいちらんに戻る」）
- 保護者向けセクションや規約類は通常の漢字表記でよい

## 11. ロードマップ

### 11.1 優先順位の考え方

当面の目標が **Xでの広報による認知拡大** であることを踏まえ、次の順で判断する。

1. **宣伝の効果に直結するか** — 宣伝を始めてから直しても、初期の流入には間に合わない
2. **後回しにすると損が累積するか** — SEO関連は効き始めるまで時間がかかるので、置くのが早いほど得
3. **サイトの価値そのものを増やすか** — 単元コンテンツ
4. **再訪を促すか** — 学習履歴など。解く物が揃ってから効く

### 11.2 フェーズ0: 宣伝を始める前に（小さい作業・効果大）

| 項目 | 理由 |
|------|------|
| OGP画像・メタタグの設定 | Xで共有したときにカードが表示されるかどうかで、クリック率が大きく変わる。**宣伝するなら最優先** |
| favicon の設定 | タブやブックマークでの識別。第一印象に効く |
| `robots.txt` を `public/` へ移動 | 現在配信されていない（→ 9章）。SEOの土台 |
| `sitemap.xml` の生成 | 同上。ページ数が少ないうちに仕組みを入れておく |

いずれも小さい作業。ここを片づけてから宣伝を始めるのが効率がよい。

### 11.3 フェーズ1: コンテンツを増やす（宣伝と並走）

分数は公開済み。続いて 時こく・時間 → 図形 の順に追加する（→ 5.5）。

**全単元が揃うのを待って宣伝を始める必要はない。**
1単元公開するごとに「◯◯ドリルを公開しました」という投稿ネタになるため、
開発と広報を噛み合わせて進められる。

### 11.4 フェーズ2: 定着させる

| 項目 | 着手の目安 |
|------|-----------|
| 学習履歴（localStorage）で前回の点数などを表示 | 単元がある程度増えてから。解く物が少ないうちは再訪動機になりにくい |
| 教科書の履修順に沿った単元構成への整理 | 単元数が増えて、一覧が並べただけでは分かりにくくなってきたら |
